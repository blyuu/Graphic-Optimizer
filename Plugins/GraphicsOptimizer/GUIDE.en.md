# Graphics Optimizer — Plugin Reference

UE 5.5 runtime/editor plugin for temporary scalability benchmarks and measured setting combinations.

## Use

1. Build the project in your normal Unreal workflow and enable the plugin if prompted.
2. Start Play In Editor with a fixed camera and stable scene.
3. Open **Tools > Graphics Optimizer**.
   The panel is organized by purpose, not a required sequence: **Quality settings** contains Scalability search, result selection, visual/motion comparisons, and apply/save controls; **Shadow casters and GPU traces** contains local shadow A/B and GPU captures; **Lumen detail and scene structure** contains Lumen A/B plus VSM/instancing candidate scans. Expand only the study you want. **Complete analysis and final decision** runs every study together and shows its combined report and final Apply/Keep choice. Quality settings is expanded initially; the other areas start collapsed. Cancel, latest-result copy, accumulated-project copy, and the history folder control remain visible above the study areas.
4. Enter target FPS and measurement duration. **Run All Analyses + Copy Report** runs the measured setting search, targeted GPU pass A/B, a VSM-risk and repeated-mesh scene scan, up to three local shadow-caster experiments, a Lumen screen-probe detail A/B, and the final baseline/recommendation image comparison in one sequence. It pauses gameplay and verifies the camera throughout. **Run Optimization (settings only)** runs the measured setting search without the other studies; the **Freeze gameplay** checkbox applies to that separate settings-only run. The Phase 2 minimum useful gain defaults to 0.75 FPS per added quality reduction and can be adjusted in the panel.
5. The plugin enables the engine's `stat unit` overlay during the run and samples its per-viewport raw Frame, Game, Draw, and GPU values. Read the live overlay and the plugin-versus-stat-unit averages under each result. The Output Log category is `LogGraphicsOptimizer`.
6. Use **Copy Settings Report**, **Copy Shadow Report**, **Copy GPU Report and Pass Analysis**, **Copy Scene Diagnosis Report**, or **Copy Lumen Detail Report** for one study. **Copy Latest Results (may include separate runs)** copies the current panel results; it is not a cumulative history. **Copy Accumulated Project Reports** copies every archived run from this project.
7. After a completed run, leave **Result number** at `-1` to select the optimizer's recommendation, or enter a numbered result row. **Capture A/B: Baseline vs Selected** pauses the current PIE world, captures the baseline and selected result at the same player camera after a one-second settle for each, and restores the settings and original pause state. The panel previews the left/right image; **Open A/B Image at Full Size** opens it for detailed inspection. The PNGs and a short note are saved under the current project's `Saved/GraphicsOptimizer/Comparisons/<timestamp>/` as `Baseline.png`, `Selected.png`, `SideBySide.png`, and `Comparison.txt`. Keep PIE visible and the camera still until capture finishes. This is a static visual comparison, not a measured image-quality score or a motion comparison.
8. **Apply Selected to PIE** changes the active PIE/game session. **Restore Pre-Apply Settings** undoes that application; ending PIE also restores the pre-apply settings. **Save Selected Preset** writes the selected full Scalability configuration to the current project's `Saved/GraphicsOptimizer/SelectedScalability.ini` without applying it. **Apply Saved Preset to PIE** reloads that file and applies it in the current session. The saved file is local to this project's Saved directory and is not automatically copied into packaged builds or applied at startup. Runtime Blueprint can call `SaveCurrentSettingsAsPreset()` and `ApplySavedPreset()` on the game instance subsystem to persist and load a local preset in a packaged game.
9. For automatic movement testing after optimization, keep the playable character in an open area and select **Run 4s A/D Motion Comparison**. The plugin sends D for two seconds and A for two seconds, returns the character to its starting transform between passes, measures baseline and selected FPS in separate four-second passes without recording, then captures two four-second frame sequences. If `ffmpeg.exe` is on the machine's PATH, it encodes `MotionAB.mp4` with baseline on the left and selected on the right. Each side shows its measured average FPS. **Open 4s Motion A/B Video** opens that file. `MotionReport.txt`, the video, and source PNG frames are stored in the current project's `Saved/GraphicsOptimizer/MotionComparisons/<timestamp>/`. The report includes average FPS, 1% low, frame/GPU time, and the difference between sampled character paths. Video playback is 24 FPS; its FPS labels are measurements from the separate passes without frame recording. If encoding fails, the PNG frames and FPS report remain available.
10. Use **Cancel and Restore** to stop an active benchmark or A/B study early.
11. For the first Phase 3 scene-level experiment, keep PIE visible on a representative scene and select **Scan Shadow Casters**. The panel lists up to 20 recently rendered static-mesh groups that currently cast dynamic shadows, including Static, Stationary, and Movable components, sorted by component count. This is a candidate inventory, not a GPU-cost ranking. Select a group number and **Benchmark Shadow Group A/B**. The plugin pauses gameplay, verifies the camera and viewport remain fixed, measures the current configuration, temporarily turns off `CastShadow` only for components in that mesh group, measures again, captures baseline/candidate PNGs and a side-by-side PNG, and restores the original flags and pause state. **Open Shadow A/B Image** shows the comparison; **Copy Shadow Report** copies the result. Outputs are saved to an absolute path under `Saved/GraphicsOptimizer/ShadowStudies/<timestamp>/`. This is a PIE runtime experiment and never saves the mesh or level changes. The report gives whole-frame FPS, 1% low, render, and GPU time; it does not claim to measure the shadow render pass separately. Movable components are tested while gameplay is paused, so this study cannot measure their movement-driven shadow cache updates. A visible quality change may make a faster result unsuitable.
12. For the targeted Phase 3 GPU test on its own, keep the PIE camera pointed at the workload and press **Run GPU Pass A/B (GI and Shadow)**. The plugin pauses gameplay and measures original, GI minus one, and Shadow minus one independently. Wait for completion, press **Analyze GPU Passes**, then **Copy GPU Report and Pass Analysis**. Open both left/right images to judge visible changes. The current settings are restored after the run. The saved files are under `Saved/GraphicsOptimizer/GpuTraces/<timestamp>/`.
13. After **Run All Analyses + Copy Report** finishes, inspect **Full analysis decision** and open the final baseline/recommendation image. The GPU pass analysis runs automatically when the panel is visible; **Copy Full Analysis Report** includes the measured setting rows, shadow-caster observations, image path, and GPU timer comparison. Choose **Apply Recommended to PIE** or **Keep Original Settings**. The former is temporary in the current PIE session; saving a preset remains a separate explicit action. Local `CastShadow` experiments are exploratory and are never applied with the Scalability recommendation. `FullAnalysisReport.txt` and the combined `FullAnalysisWithGpuPasses.txt` are stored under `Saved/GraphicsOptimizer/FullAnalyses/<timestamp>/`.
14. **Scan VSM and Instancing Candidates** can be run alone in PIE. It inventories movable shadow-casting lights, movable or WPO static-mesh casters, and repeated static mesh/material groups. These are hypotheses, not measured VSM page invalidations or draw-call savings. The report is saved under `Saved/GraphicsOptimizer/SceneDiagnostics/` or the active full-analysis folder. **Run Lumen Screen-Probe A/B** independently compares the current `r.Lumen.ScreenProbeGather.DownsampleFactor` with a larger tile factor, with one-second warmups, FPS/GPU measurements and a side-by-side image. It restores the original CVar value and pause state. Results are saved under `Saved/GraphicsOptimizer/LumenStudies/<timestamp>/`. Open the image before judging whether the detail loss is acceptable.

Both modes measure the current configuration, then independently lower Shadow, Global Illumination, Reflection, Post Process, Texture, and Effects by one scalability level where possible. Resolution scale is tested at about 10 percentage points lower when its starting percentage is known. Each experiment has a one-second warmup and uses the entered measurement duration. Settings are restored after each experiment and at the end. Selectable result objects are held in memory for the active PIE game instance and disappear when PIE ends. Completed or interrupted report snapshots are also archived on disk and survive PIE restarts; see Report history below.

**Run Optimization** ranks single-setting changes that gained more than 0.5 FPS and measures combinations. It adds a new quality reduction to the selected configuration only when the measured FPS gain reaches the panel's **Minimum useful FPS gain per extra quality reduction** (default 0.75 FPS), or when that measurement meets the target. After a configuration meets the target, it restores one changed setting at a time and remeasures. A restoration is kept only if the measured FPS still meets the target; after each successful restoration, the remaining changes are checked again. This quality-recovery pass runs in a fixed order (resolution, GI, shadow, reflection, post process, texture, effects) and stops after no single remaining change can be restored without missing the target. It is a local check, not an exhaustive search or image-quality ranking. The report distinguishes this quality-preserving candidate from the absolute fastest observation when they differ. If the target is not met, the ranked changes are exhausted, or the result approaches an effective frame cap that prevents a valid target decision, recovery does not run. A capped result is still shown as the fastest observation but is labeled target-inconclusive. The suggestion is scene-specific. Benchmarking restores original settings; applying or saving a selected result requires a separate user action.

After the search, the current selected candidate gets **three fresh validation passes**. The nearest below-target quality-recovery result within 1 FPS and the fastest original target-meeting result are also validated when they represent different configurations (at most three configurations total). Every validation row appears in the report. The summary shows each configuration's median FPS, minimum and maximum FPS, and how many of its three passes met the target. A target is considered repeatably met only when all three passes are valid and meet it. Among repeatably meeting configurations, the selection prefers fewer changed setting groups, then the higher median FPS. If none pass all three, the earlier selected candidate remains visible but the verdict says **Target not repeatably met** when the initial search had reached the target. This criterion still uses average FPS per pass; 1% low values remain visible in the individual result rows. With the default five-second measurement and one-second warmup, validation adds about 18 seconds per configuration. If the effective tick cap blocks a valid target verdict near the cap, the additional validation passes are skipped. The user exercised the three-pass path in a cap-limited run; an uncapped user validation is still pending.

GPU timing can be unavailable on some RHIs or editor configurations. In that case GPU sample count is zero and GPU comparisons are omitted. For comparable results, use the same scene and camera, keep the PIE viewport in focus, and avoid loading or compiling content during a run. Frame caps and VSync can hide improvements; their current values are logged at run start.

If the engine tick cap is at the target FPS, FPS changes near that cap are marked **capped** and the target result is **inconclusive**. The plugin does not change project frame-rate settings. Check the logged effective max tick rate, project frame smoothing/fixed frame-rate settings, and on laptops the editor's battery limit (`r.DontLimitOnBattery`) before comparing FPS. A scalability resolution value of `0` means **project default**, not 0%. The plugin observes the PIE viewport's selected primary resolution fraction from UE's screen-percentage interface; for UE's static legacy driver this is the applied fraction. Dynamic resolution is excluded. It creates a reduction candidate after a stable observation and checks the selected fraction again during the experiment. If verification fails it aborts and restores settings; if no stable baseline fraction is observed, it skips that experiment. Keep the PIE viewport drawing for several frames before starting the run. Custom screen-percentage drivers may report an upper bound rather than an exact rendered fraction, so their results need separate validation. A user run has now verified the full 100%-to-90% experiment path in PIE; the copied report does not show whether the candidate was made at start or after baseline. Render-thread timing under 0.01 ms is displayed as unavailable instead of 0.00 ms.

The render readout separates **render busy** (`GRenderThreadTime`) from **render critical path** (`GRenderThreadTimeCriticalPath`, including dependent waits). In PIE, render busy has been observed near 0.002 ms even with GPU work; this cannot be treated as a meaningful render workload estimate. The critical-path value is collected independently and labeled as such. Compare it with `stat unit` in the same PIE session. If both remain unavailable, further engine-timing investigation is needed. Freezing gameplay makes the scene repeatable for static rendering comparisons but does not represent active combat. The original pause state is restored after completion, cancellation, or failure.

The `stat unit` overlay is turned on automatically only when it was initially off, and its original on/off state is restored after the run. The per-experiment `stat unit avg` rows use the viewport's raw measurements, sampled once per drawn viewport frame. These values are more directly comparable than a single screenshot of the smoothed overlay.

If direct `RenderBusy` is unusable but the viewport's `stat unit` Draw average is valid, the primary render readout uses that Draw value and labels its source. The report still shows both data sources and warns when they disagree.

Every positive frame interval is included in FPS and 1% low calculations, including frames longer than one second. The panel and log flag frames of at least 250 ms as long hitches; a run with such hitches should be repeated before comparing settings.

## Report history and one-button copying (2026-09-28)

UE 5.5 UHT and C++ compilation passed with -NoLink on 2026-09-28. DLL linking and PIE validation are pending for this revision; the editor was running during the compilation check.

- **Individual runs:** use Run Settings Benchmark for independent one-level changes, or Run Optimization for the measured combination search. The dedicated settings copy includes all measured rows, validation results, settings and sample counts. Shadow, GPU, scene diagnosis and Lumen each have their own copy control. GPU copying analyzes a pending trace first.
- **One-button run:** Run All Analyses + Copy Report runs settings optimization, GPU baseline/GI/shadow traces, VSM/instancing inventory, up to three shadow groups, Lumen detail A/B, then the final baseline/recommendation images. While the panel remains open, completion automatically analyzes the GPU traces and copies the consolidated report to the clipboard. Cancellation or a failed stage copies a clearly stopped partial report. Apply/Keep remains an explicit choice. Automatic copying does not happen after PIE has ended or the panel has been closed; the runtime report snapshots remain on disk.
- **Scope:** the combined report covers this full-analysis invocation. A standalone study performed later is a separate record; its GPU analysis must not be appended to an older full report. Motion recording remains a separate action because it requires a movable character and different test conditions. Static/motion comparisons also get archived when they finish or stop.
- **Persistent history:** accepted studies that finish or stop write records under the current project's Saved/GraphicsOptimizer/ReportHistory/<PIE-session timestamp and ID>/<sequence and ID>/Report.txt. Each record includes its category, run identity, update time and report. A repeat run creates a new record. Later GPU timer analysis or an Apply/Keep decision updates the same run's record instead of adding a duplicate.
- **Copy Accumulated Project Reports** reads those records across PIE sessions and writes AccumulatedReport.txt beside the session folders as well as copying it. Open Report History Folder opens that location. Full records repeat some constituent study results: record count is not a count of independent benchmark samples. Different scenes/cameras/settings must not be treated as one comparable experiment.
- **Existing results:** earlier output folders and reports documented in Docs/BenchmarkResults are preserved. They are not automatically reconstructed into the new history; automatic accumulation begins with this revision. Saved directories are project-local and are not guaranteed to be included in source control.

### Verification after rebuilding

1. Run a settings benchmark and copy its report; confirm a Settings record exists in ReportHistory.
2. Run a standalone shadow study and GPU capture, copy each report (GPU copy should include timer analysis), then copy accumulated reports. Confirm three distinct run records and their paths/timestamps.
3. Repeat one study: the count should increase. Copy/analyze it again: the count should not increase.
4. Restart PIE and copy accumulated reports: the earlier records should remain.
5. Run All Analyses + Copy Report with the panel open and PIE focused. After completion, paste directly: the full report should include GPU timer analysis and all reached stages. Cancel one run and confirm a stopped report with the reason and unavailable stages.
6. Run another standalone GPU study afterward: the previous full report must retain its own GPU comparison, rather than use the new capture. Apply/Keep should update its recorded decision without losing that comparison.
