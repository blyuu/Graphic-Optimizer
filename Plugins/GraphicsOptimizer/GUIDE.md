# Graphics Optimizer — 플러그인 상세 설명서

UE 5.5 런타임/에디터 플러그인으로, 일시적인 스케일러빌리티(Scalability) 벤치마크와 측정 기반 설정 조합 탐색을 수행합니다.

## 사용 방법

1. 평소의 언리얼 워크플로우대로 프로젝트를 빌드하고, 활성화하라는 메시지가 뜨면 플러그인을 활성화합니다.
2. 고정된 카메라와 안정적인 씬으로 Play In Editor(PIE)를 시작합니다.
3. **Tools > Graphics Optimizer**를 엽니다. 패널은 반드시 따라야 할 순서가 아니라 목적별로 구성되어 있습니다: **Quality settings**에는 Scalability 탐색, 결과 선택, 비주얼/모션 비교, 적용/저장 컨트롤이 들어 있고; **Shadow casters and GPU traces**에는 로컬 섀도우 A/B와 GPU 캡처가; **Lumen detail and scene structure**에는 Lumen A/B와 VSM/인스턴싱 후보 스캔이 들어 있습니다. 원하는 스터디만 펼치면 됩니다. **Complete analysis and final decision**은 모든 스터디를 한 번에 실행하고 통합 리포트와 최종 Apply/Keep 선택지를 보여줍니다. Quality settings는 처음부터 펼쳐져 있고, 나머지 영역은 접힌 상태로 시작합니다. Cancel, 최신 결과 복사, 누적 프로젝트 복사, 히스토리 폴더 컨트롤은 스터디 영역들 위에 항상 표시됩니다.
4. 목표 FPS와 측정 시간을 입력합니다. **Run All Analyses + Copy Report**는 측정 기반 설정 탐색, 타깃 GPU 패스 A/B, VSM 위험도 및 반복 메시 씬 스캔, 최대 3개의 로컬 섀도우 캐스터 실험, Lumen 스크린 프로브 상세 A/B, 그리고 마지막 베이스라인/추천 이미지 비교를 하나의 시퀀스로 실행합니다. 이 전체 과정 동안 게임플레이를 일시정지하고 카메라를 계속 검증합니다. **Run Optimization (settings only)**은 다른 스터디 없이 측정 기반 설정 탐색만 실행합니다; **Freeze gameplay** 체크박스는 이 별도의 설정 전용 실행에 적용됩니다. Phase 2의 최소 유효 이득은 기본값이 추가 화질 저하 1단계당 0.75 FPS이며 패널에서 조정할 수 있습니다.
5. 플러그인은 실행 중 엔진의 `stat unit` 오버레이를 활성화하고, 뷰포트별 원시 Frame/Game/Draw/GPU 값을 샘플링합니다. 실시간 오버레이와 각 결과 아래 표시되는 플러그인 대 `stat unit` 평균값을 함께 확인하세요. 출력 로그 카테고리는 `LogGraphicsOptimizer`입니다.
6. 개별 스터디에 대해서는 **Copy Settings Report**, **Copy Shadow Report**, **Copy GPU Report and Pass Analysis**, **Copy Scene Diagnosis Report**, **Copy Lumen Detail Report** 중 하나를 사용합니다. **Copy Latest Results (may include separate runs)**는 현재 패널의 결과를 복사하는 것이며 누적 히스토리가 아닙니다. **Copy Accumulated Project Reports**는 이 프로젝트에 보관된 모든 실행 기록을 복사합니다.
7. 실행이 완료된 후, **Result number**를 `-1`로 두면 옵티마이저의 추천 결과가 선택되고, 특정 번호를 입력하면 해당 결과 행이 선택됩니다. **Capture A/B: Baseline vs Selected**는 현재 PIE 월드를 일시정지하고, 각각 1초의 안정화 시간 후 동일한 플레이어 카메라에서 베이스라인과 선택된 결과를 캡처한 뒤, 설정과 원래 일시정지 상태를 복원합니다. 패널은 좌/우 이미지를 미리보기로 보여주며, **Open A/B Image at Full Size**로 상세 확인을 위해 원본 크기로 열 수 있습니다. PNG 파일과 짧은 노트는 현재 프로젝트의 `Saved/GraphicsOptimizer/Comparisons/<timestamp>/`에 `Baseline.png`, `Selected.png`, `SideBySide.png`, `Comparison.txt`로 저장됩니다. 캡처가 끝날 때까지 PIE 화면과 카메라를 그대로 유지하세요. 이는 정적 비주얼 비교이며, 측정된 이미지 품질 점수나 모션 비교가 아닙니다.
8. **Apply Selected to PIE**는 현재 활성화된 PIE/게임 세션을 변경합니다. **Restore Pre-Apply Settings**는 그 적용을 되돌리며, PIE를 종료해도 적용 전 설정으로 복원됩니다. **Save Selected Preset**은 선택된 전체 Scalability 설정을 현재 프로젝트의 `Saved/GraphicsOptimizer/SelectedScalability.ini`에 적용하지 않고 저장만 합니다. **Apply Saved Preset to PIE**는 그 파일을 다시 불러와 현재 세션에 적용합니다. 저장된 파일은 이 프로젝트의 Saved 디렉터리에 로컬로 존재하며, 패키지 빌드에 자동으로 복사되거나 시작 시 자동 적용되지 않습니다. 런타임 블루프린트에서는 게임 인스턴스 서브시스템의 `SaveCurrentSettingsAsPreset()`과 `ApplySavedPreset()`을 호출해 패키지된 게임에서도 로컬 프리셋을 저장·로드할 수 있습니다.
9. 최적화 이후 자동 이동 테스트를 하려면, 플레이 가능한 캐릭터를 트인 공간에 두고 **Run 4s A/D Motion Comparison**을 선택합니다. 플러그인은 2초간 D, 2초간 A 입력을 보내고, 각 패스 사이에 캐릭터를 시작 트랜스폼으로 되돌린 뒤, 녹화 없이 별도의 4초 패스로 베이스라인과 선택된 결과의 FPS를 측정하고, 그다음 4초짜리 프레임 시퀀스 두 개를 캡처합니다. 머신의 PATH에 `ffmpeg.exe`가 있으면 왼쪽에 베이스라인, 오른쪽에 선택된 결과를 배치한 `MotionAB.mp4`를 인코딩합니다. 각 쪽에는 측정된 평균 FPS가 표시됩니다. **Open 4s Motion A/B Video**로 그 파일을 엽니다. `MotionReport.txt`, 비디오, 원본 PNG 프레임은 현재 프로젝트의 `Saved/GraphicsOptimizer/MotionComparisons/<timestamp>/`에 저장됩니다. 리포트에는 평균 FPS, 1% low, 프레임/GPU 시간, 그리고 샘플링된 캐릭터 경로 간 차이가 포함됩니다. 비디오 재생은 24 FPS이며, FPS 라벨은 프레임 녹화 없이 진행된 별도의 측정 패스에서 나온 값입니다. 인코딩이 실패하더라도 PNG 프레임과 FPS 리포트는 그대로 남습니다.
10. 진행 중인 벤치마크나 A/B 스터디를 조기에 중단하려면 **Cancel and Restore**를 사용합니다.
11. 첫 번째 Phase 3 씬 레벨 실험을 위해서는, 대표성 있는 씬에서 PIE를 유지한 채 **Scan Shadow Casters**를 선택합니다. 패널은 현재 동적 그림자를 드리우는 최근 렌더링된 스태틱 메시 그룹(Static·Stationary·Movable 컴포넌트 포함)을 컴포넌트 개수순으로 최대 20개까지 나열합니다. 이는 GPU 비용 순위가 아니라 후보 목록입니다. 그룹 번호를 선택하고 **Benchmark Shadow Group A/B**를 실행하면, 플러그인은 게임플레이를 일시정지하고 카메라와 뷰포트가 고정되었는지 확인한 뒤, 현재 설정을 측정하고, 해당 메시 그룹의 컴포넌트에 대해서만 일시적으로 `CastShadow`를 끄고 다시 측정하며, 베이스라인/후보 PNG와 side-by-side PNG를 캡처한 뒤 원래 플래그와 일시정지 상태를 복원합니다. **Open Shadow A/B Image**로 비교 결과를 확인하고, **Copy Shadow Report**로 결과를 복사합니다. 출력물은 `Saved/GraphicsOptimizer/ShadowStudies/<timestamp>/` 아래 절대 경로에 저장됩니다. 이는 PIE 런타임 실험이며 메시나 레벨 변경 사항을 저장하지 않습니다. 리포트는 전체 프레임 FPS, 1% low, 렌더·GPU 시간을 제공하며, 섀도우 렌더 패스만 따로 측정한다고 주장하지 않습니다. Movable 컴포넌트는 게임플레이가 일시정지된 상태에서 테스트되므로, 이 스터디는 이동에 의해 발생하는 섀도우 캐시 업데이트를 측정할 수 없습니다. 눈에 띄는 화질 변화가 있다면 더 빠른 결과가 적합하지 않을 수 있습니다.
12. 단독으로 타깃 Phase 3 GPU 테스트를 하려면, PIE 카메라를 워크로드에 고정한 채 **Run GPU Pass A/B (GI and Shadow)**를 누릅니다. 플러그인은 게임플레이를 일시정지하고 원본, GI 1단계 감소, Shadow 1단계 감소를 각각 독립적으로 측정합니다. 완료를 기다린 뒤 **Analyze GPU Passes**를 누르고, 그다음 **Copy GPU Report and Pass Analysis**를 누릅니다. 눈에 보이는 변화를 판단하려면 좌/우 이미지를 모두 열어 확인하세요. 실행 후 현재 설정은 복원됩니다. 저장된 파일은 `Saved/GraphicsOptimizer/GpuTraces/<timestamp>/` 아래에 있습니다.
13. **Run All Analyses + Copy Report**가 끝나면 **Full analysis decision**을 확인하고 최종 베이스라인/추천 이미지를 엽니다. GPU 패스 분석은 패널이 열려 있는 동안 자동으로 실행되며, **Copy Full Analysis Report**에는 측정된 설정 행들, 섀도우 캐스터 관찰 결과, 이미지 경로, GPU 타이머 비교가 포함됩니다. **Apply Recommended to PIE** 또는 **Keep Original Settings** 중 하나를 선택합니다. 전자는 현재 PIE 세션에서만 임시로 적용되며, 프리셋 저장은 여전히 별도의 명시적 동작입니다. 로컬 `CastShadow` 실험은 탐색적 성격이며 Scalability 추천과 함께 적용되는 일은 없습니다. `FullAnalysisReport.txt`와 통합된 `FullAnalysisWithGpuPasses.txt`는 `Saved/GraphicsOptimizer/FullAnalyses/<timestamp>/`에 저장됩니다.
14. **Scan VSM and Instancing Candidates**는 PIE에서 단독으로 실행할 수 있습니다. 이동 가능한 섀도우 캐스팅 라이트, 이동 가능하거나 WPO를 사용하는 스태틱 메시 캐스터, 그리고 반복되는 스태틱 메시/머티리얼 그룹을 인벤토리화합니다. 이는 측정된 VSM 페이지 무효화나 드로우콜 절감이 아니라 가설입니다. 리포트는 `Saved/GraphicsOptimizer/SceneDiagnostics/` 또는 활성화된 전체 분석 폴더 아래에 저장됩니다. **Run Lumen Screen-Probe A/B**는 현재 `r.Lumen.ScreenProbeGather.DownsampleFactor`와 더 큰 타일 팩터를 각각 1초 워밍업, FPS/GPU 측정, side-by-side 이미지와 함께 독립적으로 비교합니다. 원래의 CVar 값과 일시정지 상태를 복원합니다. 결과는 `Saved/GraphicsOptimizer/LumenStudies/<timestamp>/`에 저장됩니다. 디테일 손실이 허용 가능한지 판단하기 전에 이미지를 먼저 열어 확인하세요.

두 실행 모드 모두 현재 설정을 측정한 뒤, 가능한 경우 Shadow, Global Illumination, Reflection, Post Process, Texture, Effects를 독립적으로 한 단계씩 낮춰 측정합니다. 시작 퍼센티지를 알 수 있을 때는 Resolution Scale을 약 10%p 낮춰 테스트합니다. 각 실험은 1초의 워밍업을 거치며 입력된 측정 시간을 사용합니다. 각 실험 이후와 종료 시 설정이 복원됩니다. 선택 가능한 결과 객체는 활성 PIE 게임 인스턴스에 대해 메모리에 유지되며 PIE가 종료되면 사라집니다. 완료되었거나 중단된 리포트 스냅샷은 디스크에도 아카이브되어 PIE 재시작 후에도 남아 있습니다. 자세한 내용은 아래 "리포트 히스토리"를 참고하세요.

**Run Optimization**은 0.5 FPS 이상 이득을 얻은 단일 설정 변경들을 순위화하고 조합을 측정합니다. 측정된 FPS 이득이 패널의 **Minimum useful FPS gain per extra quality reduction**(기본 0.75 FPS)에 도달하거나, 그 측정값이 목표를 만족할 때만 선택된 설정에 새로운 화질 저하를 추가합니다. 설정이 목표를 만족하면, 변경된 설정을 하나씩 원복하며 다시 측정합니다. 복원은 복원 후에도 측정된 FPS가 여전히 목표를 만족할 때만 유지되며, 성공적인 복원 이후에는 남은 변경 사항들을 다시 확인합니다. 이 품질 회복 패스는 고정된 순서(resolution, GI, shadow, reflection, post process, texture, effects)로 진행되며, 목표를 놓치지 않고 남은 어떤 변경도 복원할 수 없을 때 멈춥니다. 이는 전수 탐색이나 이미지 품질 순위화가 아니라 국소적인 확인입니다. 리포트는 이 품질 보존 후보와 절대적으로 가장 빠른 관측값이 서로 다를 때 이를 구분해 보여줍니다. 목표가 충족되지 않았거나, 순위화된 변경들이 모두 소진되었거나, 결과가 유효한 목표 판정을 방해하는 유효 프레임 상한에 근접한 경우 회복 패스는 실행되지 않습니다. 상한에 걸린 결과도 가장 빠른 관측값으로는 표시되지만 target-inconclusive로 라벨링됩니다. 제안은 해당 씬에 특화된 것입니다. 벤치마킹은 원래 설정을 복원하며, 선택된 결과의 적용이나 저장은 별도의 사용자 조작이 필요합니다.

탐색이 끝나면 현재 선택된 후보는 **3회의 새로운 검증 패스**를 거칩니다. 목표에 1 FPS 이내로 근접한 품질 회복 결과와, 원본 목표 충족 결과 중 가장 빠른 것도 서로 다른 설정을 나타낼 경우 함께 검증됩니다(최대 3개 설정까지). 모든 검증 행이 리포트에 표시됩니다. 요약에는 각 설정의 중앙값 FPS, 최소/최대 FPS, 그리고 3회 패스 중 몇 회가 목표를 만족했는지가 표시됩니다. 목표는 3회 패스 모두가 유효하고 목표를 만족할 때만 "반복 가능하게 달성됨"으로 간주됩니다. 반복적으로 목표를 만족하는 설정들 중에서는 변경된 설정 그룹 수가 적은 쪽을, 그다음으로 중앙값 FPS가 높은 쪽을 우선합니다. 만약 셋 중 하나도 모두 통과하지 못하면, 초기 탐색이 목표에 도달했었다는 전제하에 이전에 선택된 후보가 그대로 표시되지만 판정은 **Target not repeatably met**으로 표시됩니다. 이 기준은 여전히 패스당 평균 FPS를 사용하며, 1% low 값은 개별 결과 행에서 계속 확인할 수 있습니다. 기본값인 5초 측정과 1초 워밍업 기준으로, 검증은 설정당 약 18초를 추가합니다. 유효 틱 상한이 상한 근처에서 유효한 목표 판정을 막는 경우, 추가 검증 패스는 건너뜁니다.

GPU 타이밍은 일부 RHI나 에디터 구성에서 사용할 수 없을 수 있습니다. 이 경우 GPU 샘플 수는 0이 되고 GPU 비교는 생략됩니다. 비교 가능한 결과를 얻으려면 동일한 씬과 카메라를 사용하고, PIE 뷰포트에 포커스를 유지하며, 실행 중 콘텐츠 로딩이나 컴파일을 피하세요. 프레임 상한과 VSync는 개선 효과를 가릴 수 있으며, 실행 시작 시 현재 값이 로그에 기록됩니다.

엔진 틱 상한이 목표 FPS와 같다면, 그 상한 근처의 FPS 변화는 **capped**로 표시되고 목표 결과는 **inconclusive**가 됩니다. 플러그인은 프로젝트의 프레임레이트 설정을 변경하지 않습니다. FPS를 비교하기 전에 로그에 기록된 유효 최대 틱레이트, 프로젝트의 프레임 스무딩/고정 프레임레이트 설정, 그리고 노트북이라면 에디터의 배터리 제한(`r.DontLimitOnBattery`)을 확인하세요. Scalability의 resolution 값 `0`은 0%가 아니라 **프로젝트 기본값**을 의미합니다. 플러그인은 UE의 화면 비율(screen-percentage) 인터페이스로부터 PIE 뷰포트에서 선택된 기본 해상도 비율을 관찰합니다. UE의 정적 레거시 드라이버의 경우 이는 실제 적용된 비율입니다. 동적 해상도는 제외됩니다. 안정적인 관측 이후 감소 후보를 만들고, 실험 중 선택된 비율을 다시 확인합니다. 검증에 실패하면 중단하고 설정을 복원하며, 안정적인 베이스라인 비율이 관측되지 않으면 해당 실험을 건너뜁니다. 실행을 시작하기 전 PIE 뷰포트가 여러 프레임 동안 그려지고 있도록 유지하세요. 커스텀 화면 비율 드라이버는 정확한 렌더링 비율이 아니라 상한값을 보고할 수 있으므로, 그 결과는 별도의 검증이 필요합니다. 0.01 ms 미만의 렌더 스레드 타이밍은 0.00 ms 대신 "사용 불가"로 표시됩니다.

렌더 판독값은 **render busy**(`GRenderThreadTime`)와 **render critical path**(`GRenderThreadTimeCriticalPath`, 종속 대기 포함)를 구분합니다. PIE에서 render busy는 GPU 작업이 있어도 0.002 ms 근처로 관측된 적이 있으며, 이는 의미 있는 렌더 워크로드 추정치로 취급할 수 없습니다. critical-path 값은 독립적으로 수집되어 그렇게 라벨링됩니다. 같은 PIE 세션의 `stat unit`과 비교해 보세요. 둘 다 사용 불가라면 추가적인 엔진 타이밍 조사가 필요합니다. 게임플레이를 정지시키면 정적 렌더링 비교를 위한 반복 가능한 씬을 만들 수 있지만, 실제 전투 상황을 대표하지는 않습니다. 원래의 일시정지 상태는 완료, 취소, 실패 이후 복원됩니다.

`stat unit` 오버레이는 초기에 꺼져 있었을 때만 자동으로 켜지며, 실행 후 원래의 on/off 상태로 복원됩니다. 실험별 `stat unit avg` 행은 뷰포트의 원시 측정값을 사용하며, 그려진 뷰포트 프레임마다 한 번씩 샘플링됩니다. 이 값들은 부드럽게 처리된 오버레이의 단일 스크린샷보다 더 직접적으로 비교 가능합니다.

직접적인 `RenderBusy`를 사용할 수 없지만 뷰포트의 `stat unit` Draw 평균이 유효한 경우, 주요 렌더 판독값은 그 Draw 값을 사용하며 출처를 라벨링합니다. 리포트는 두 데이터 출처를 모두 보여주며 서로 값이 다를 때 경고를 표시합니다.

1초보다 긴 프레임을 포함해, 양수인 모든 프레임 간격이 FPS와 1% low 계산에 포함됩니다. 패널과 로그는 250ms 이상의 프레임을 긴 히치(hitch)로 표시하며, 이런 히치가 있는 실행은 설정을 비교하기 전에 반복해야 합니다.

## 리포트 히스토리와 원버튼 복사

- **개별 실행:** 독립적인 단일 단계 변경에는 Run Settings Benchmark를, 측정 기반 조합 탐색에는 Run Optimization을 사용합니다. 전용 설정 복사에는 측정된 모든 행, 검증 결과, 설정, 샘플 수가 포함됩니다. Shadow, GPU, 씬 진단, Lumen은 각각 자체 복사 컨트롤을 가집니다. GPU 복사는 대기 중인 트레이스를 먼저 분석합니다.
- **원버튼 실행:** Run All Analyses + Copy Report는 설정 최적화, GPU 베이스라인/GI/섀도우 트레이스, VSM/인스턴싱 인벤토리, 최대 3개의 섀도우 그룹, Lumen 상세 A/B, 그리고 마지막 베이스라인/추천 이미지를 실행합니다. 패널이 열려 있는 동안, 완료 시 자동으로 GPU 트레이스를 분석하고 통합 리포트를 클립보드에 복사합니다. 취소되었거나 어떤 단계가 실패하면 명확히 중단되었음을 알리는 부분 리포트를 복사합니다. Apply/Keep은 여전히 명시적인 선택으로 남습니다. PIE가 종료되었거나 패널이 닫힌 이후에는 자동 복사가 일어나지 않으며, 런타임 리포트 스냅샷은 디스크에 남아 있습니다.
- **범위:** 통합 리포트는 이 전체 분석 실행 범위를 다룹니다. 나중에 수행된 단독 스터디는 별도의 기록이며, 그 GPU 분석이 예전의 전체 리포트에 추가되어서는 안 됩니다. 모션 녹화는 이동 가능한 캐릭터와 다른 테스트 조건이 필요하므로 별도의 동작으로 남습니다. 정적/모션 비교도 완료되거나 중단될 때 아카이브됩니다.
- **영구 히스토리:** 완료되거나 중단된 스터디는 현재 프로젝트의 `Saved/GraphicsOptimizer/ReportHistory/<PIE 세션 타임스탬프와 ID>/<순번과 ID>/Report.txt` 아래에 기록됩니다. 각 기록에는 카테고리, 실행 식별자, 갱신 시각, 리포트가 포함됩니다. 반복 실행은 새 기록을 생성합니다. 이후의 GPU 타이머 분석이나 Apply/Keep 결정은 중복 기록을 추가하는 대신 동일한 실행 기록을 갱신합니다.
- **Copy Accumulated Project Reports**는 PIE 세션 전체에 걸친 그 기록들을 읽어, 세션 폴더들 옆에 `AccumulatedReport.txt`를 작성하고 동시에 복사합니다. Open Report History Folder는 그 위치를 엽니다. 전체 기록은 일부 구성 스터디 결과를 반복해서 담고 있으므로, 기록 개수가 독립적인 벤치마크 샘플 개수를 의미하지는 않습니다. 서로 다른 씬/카메라/설정은 하나의 비교 가능한 실험으로 취급해서는 안 됩니다.
- **기존 결과:** `Docs/BenchmarkResults`에 문서화된 이전 출력 폴더와 리포트는 그대로 보존됩니다. 이들은 새 히스토리 체계로 자동 재구성되지 않으며, 자동 누적은 이 리비전부터 시작됩니다. Saved 디렉터리는 프로젝트 로컬이며 소스 관리에 포함된다는 보장은 없습니다.

### 재빌드 후 검증

1. 설정 벤치마크를 실행하고 리포트를 복사한 뒤, ReportHistory에 Settings 기록이 존재하는지 확인합니다.
2. 독립적인 섀도우 스터디와 GPU 캡처를 실행하고 각각의 리포트를 복사한(GPU 복사는 타이머 분석을 포함해야 함) 뒤, 누적 리포트를 복사합니다. 서로 다른 3개의 실행 기록과 그 경로/타임스탬프를 확인합니다.
3. 하나의 스터디를 반복 실행합니다: 개수가 증가해야 합니다. 다시 복사/분석합니다: 개수가 증가하지 않아야 합니다.
4. PIE를 재시작하고 누적 리포트를 복사합니다: 이전 기록이 남아 있어야 합니다.
5. 패널을 열고 PIE에 포커스를 둔 채 Run All Analyses + Copy Report를 실행합니다. 완료 후 바로 붙여넣습니다: 전체 리포트에는 GPU 타이머 분석과 도달한 모든 단계가 포함되어야 합니다. 하나의 실행을 취소하고, 사유와 사용 불가능한 단계가 표시된 중단 리포트를 확인합니다.
6. 그 이후 또 다른 독립적인 GPU 스터디를 실행합니다: 이전의 전체 리포트는 새 캡처를 사용하는 대신 자신의 GPU 비교 결과를 그대로 유지해야 합니다. Apply/Keep은 그 비교 결과를 잃지 않고 기록된 결정만 갱신해야 합니다.
